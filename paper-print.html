The execution gap in agentic bioinformatics

A fixed-model comparison of the Biomni, Galaxy and smarts.bio tool servers against an untooled control

Nir Orpaz

smarts.bio, Tel Aviv, Israel · ORCID 0009-0004-7037-040X · Correspondence: nir@smarts.bio

Study period: 2–12 November 2026 · Model: claude-opus-5, identical in all conditions

Abstract

Whether an analysis can be executed, rather than how well a model reasons about it, is the first-order determinant of performance on realistic bioinformatics tasks. Published comparisons of agentic bioinformatics systems vary the language model, the tools and the agent architecture at once. Here we held the model (claude-opus-5) and 48 frozen prompts fixed and varied only the tool server: one of three platforms’ tool servers (Biomni, Galaxy or smarts.bio) or no tools, with the model’s own shell, web-search and code execution disabled throughout. Answers were graded 0–3 by a judge blinded to condition, then audited against primary sources and identifier registries. Mean scores over 46 tasks were 2.70 (smarts.bio), 2.30 (Biomni), 2.00 (Galaxy) and 1.00 (no tools); acceptable-answer rates were 93.5%, 78.3%, 67.4% and 28.3%, and raw scores over all 48 tasks preserved the ordering. Without tools the model scored 0.00 on NGS pipelines and 0.33 on expression analysis, but 2.25 on database lookups against a pooled tool-enabled 2.38: model knowledge substitutes for tools where the answer is a stored fact, and fails where it must be computed from data. The tool-enabled conditions spanned 2.00 to 2.70, roughly half the 1.33-point gap to the control. That ordering is sensitive to at least six smarts.bio cells re-run during the study. With their earlier scores, smarts.bio scores 2.52 and still leads, though its lead over Biomni is not significant. Because some tool servers call models of their own and each cell was run once, these are differences between tool servers under a common agent, not between the platforms as their designers deploy them.

Keywords: agentic systems; bioinformatics; tool use; large language models; benchmark; reproducibility; LLM-as-judge; computational biology

1. Introduction

A general-purpose language model can describe how to call variants from an alignment file, quantify expression or search a sequence database. Whether it can perform those operations is a separate question. Explanation draws on parametric knowledge; execution requires reading the user's files, invoking the relevant software and verifying what comes back. In practical scientific workflows the second capability may matter more than the first, because the answer depends on data the model has never seen.

Benchmarks of language models in biology have moved steadily toward this distinction. LAB-Bench assembled over 2,400 questions covering practical research capabilities (literature retrieval, figure interpretation, database navigation and sequence manipulation), establishing the breadth of activity expected of a research assistant [1]. BixBench moved further toward computational biology, evaluating agents on real analytical scenarios requiring dataset exploration and multi-step work, and reported accuracy near 17% for frontier models on open-answer tasks, far below their performance on knowledge recall [2]. The gap between those two results is the gap between knowing and doing: the execution gap, and the subject of this paper.

Systems that attempt to close it take different architectural positions. Biomni is a general-purpose biomedical agent that mines tools, databases and protocols from the literature across 25 domains and combines model reasoning with retrieval-augmented planning and code execution [3,4]. Galaxy, by contrast, is a mature workflow platform whose design goals centre on accessible, reproducible and collaborative analysis with explicit provenance, and which has recently added general-purpose GPU access and licensed-tool support [5]. smarts.bio, operated by this study's author and disclosed as such throughout (§8), takes a third position: a curated catalogue of hosted tools and multi-step pipelines that the model invokes directly, without writing or executing code on the user's behalf. These embody distinct traditions: agentic orchestration of heterogeneous tools, structured workflow execution in a shared environment, and direct invocation of a fixed tool catalogue. They also differ on an axis that cuts across those traditions: whether the system reaches a result by generating and running code, as Biomni does, or by calling pre-built tools, as the other two do. We selected these three as the clearest available instances of each position. Galaxy is among the most widely used hosted analysis platforms in the field [5]. Biomni is among the most prominent agentic systems, and the only one of the three with a published evaluation in the primary literature [4]. smarts.bio pairs its catalogue with managed CPU and GPU compute.

A parallel line of work argues that outcome correctness alone is an inadequate measure of an agent's scientific work. PromptBio-Bench evaluates end-to-end bioinformatics tasks against expert reference output files across 244 curated tasks [6]. BiomniBench scores the agent's full trajectory against task-specific expert rubrics, reporting that agents reliably ground claims in real sources yet fall short on method selection and biological interpretation, and that the agent harness shifts scores by more than the gap between successive model generations [7]. BioAgent Bench evaluates concrete workflow artifacts and robustness under controlled perturbations [8]. Each of these varies the model, the harness, or both.

The present study asks a narrower question. Some of this work does isolate parts of it: Biomni's own evaluation compares an untooled base model, a coding agent, an ablated variant and the full system, which separates tool access from planning style within one architecture [3,4]. What is missing is a comparison that holds the base model and the task set fixed while varying only which platform's tools are reachable. Such a design isolates the contribution of the platform layer from that of the model driving it, and separates two questions: how much of bioinformatics is answerable from parametric knowledge alone, and, conditional on tool access mattering, how far apart the available platforms are. The first admits a decisive answer. The second does not, for the reasons set out in §5.

The question is worth asking because it has a plausible null answer. A frontier model carries a great deal of biology in its parameters, and much of what a working scientist asks is a matter of record: what a gene does, which variant is pathogenic, what a structure looks like. If parametric knowledge were close to sufficient for the work actually brought to these systems, the platform layer would be a convenience rather than a capability, the measured differences between platforms would be small, and the sensible engineering conclusion would be to invest in models rather than in infrastructure. The untooled condition is included to test that proposition, not to furnish a floor: it is the null hypothesis of this study. Our results do not permit a single verdict on it. It holds on the categories where an answer is a stored fact, and fails comprehensively wherever an answer must be computed from data the model has never seen.

2. Methods

2.1 Conditions

Two terms are used throughout. A tool server is the network endpoint through which the model runs a platform's software: it advertises the operations available and executes the ones the model calls. Parametric knowledge is what the model can state from training alone, without consulting any source while it answers.

Four conditions, all running claude-opus-5 at the provider's default sampling settings, identical across conditions, with an identical system prompt. No condition received platform-specific prompting. We note in §5.1 that this is a fairness guarantee and a confound simultaneously.

Listed alphabetically, not by outcome. Biomni: hosted tool server. Galaxy: the galaxy-mcp server connected to a public Galaxy instance. smarts.bio: hosted tool server providing managed CPU and GPU compute and multi-step pipelines. No tools: the same model with every tool disabled, serving as the control. Results tables and figures order the conditions by outcome, as is conventional.

In all four conditions the model's built-in shell access, web search, file reading and local code execution were disabled by launch flag rather than by instruction, and the harness configured exactly one tool server per run with no fallback. A tool-enabled condition could therefore act only through its own platform's server, and could not route around a weak platform by writing code; the control could answer only from parametric knowledge.

What a condition is, precisely. Each tool-enabled condition is a platform's tool-server endpoint driven by a uniform external agent, not that platform as its designers deploy it. Reaching a system this way exposes its tool inventory but not necessarily the planning and execution architecture built around those tools, a distinction that matters materially for Biomni and Galaxy and whose consequences are set out in §5.2. We use "condition" rather than "platform" throughout the Results for this reason, and the distinction holds for every between-condition number in §3.

The fixed model is the agent, not the whole computation. Holding the model constant fixes the agent that plans and calls tools. It does not remove model-dependent computation from inside a platform's tool layer, and two of the three tool-enabled conditions call a language model of their own behind some endpoints. Biomni serves 35 of its 144 tools as natural-language prompt wrappers that its own model turns into an API query; these account for 82 calls across 24 of its 46 primary runs, 26 of them in the database-lookup category, which is the one category Biomni wins. The smarts.bio condition exposes an agent endpoint and a file-analysis endpoint that likewise call a model, together 39 calls across 15 of its 46 primary runs. The Galaxy condition made no such call. These internal calls are part of each platform as its designers ship it, and disabling them would have measured something no user can obtain, so they were left in place. Two consequences follow. Between-condition differences include whatever those internal models contribute, and the conditions are not equal in total model computation even though the driving agent is identical. The per-call counts above are recoverable from the released transcripts.

2.2 Tasks

Forty-eight tasks spanning eleven categories were written and frozen before the first run. The frozen task file is released with the dataset; it was not held in version control at the time, so we cannot offer a commit hash as independent evidence of the freeze date. The freeze is therefore an assertion by the author, not a verifiable fact. Prompts are phrased as a working scientist would type them and never name a tool, so tool discovery is part of what is measured. Where deterministic ground truth existed it came either from synthetic fixtures with planted answers (six known single-nucleotide variant positions at defined coordinates and depths; exact feature counts) or from public registries (accessions, published binding affinities).

Two tasks were found post hoc to be defective in their own material and are excluded from every condition: one prompt shipped without its input sequence, making the required identification impossible, and one supplied a GRCh37 variant file whose header declared GRCh38, so the promised consequence classifications were unreachable for any condition. Both defects are ours and were found by audit, not by inspection of results.

Because the set is self-authored, its composition is a design choice rather than a sample, and it is therefore given in full (Figure 1) rather than summarised.

2.3 Execution

Each run was a single headless model invocation with one tool server attached. Long-running jobs were handled by resuming the same session at a fixed interval with a neutral check-in message until an answer arrived or the task's pre-specified timeout elapsed. Timeout budgets were set per task before any run and were identical across conditions. Wall time is measured from first prompt to final answer. A task that timed out scores 0 on the intention-to-complete principle: the user received nothing. Failures of our own measurement harness are excluded rather than scored. Platform-side failures are not excluded: a run blocked by an exhausted compute quota, a saturated rate limit or an unavailable service is scored on what the user actually received, on the same principle that governs timeouts.

Cells that were run again. The harness as first written did not resume a session when the model returned control while a long-running job was still executing, and a resume loop was added during the study. One cell was run again for that reason. Others were run again after failures on the platform side: two where a file could not be read from smarts.bio's object storage, one where a container's cold start exceeded the task's window and the job completed after the answer had been given, and one where smarts.bio's tool server exposed no tools. Re-running those departs from the rule stated above, under which a platform-side failure is scored on what the user actually received. One further cell was run again after its score was disputed in the audit rather than after any failure, and on the primary basis it scored lower the second time. The cells so identified fell almost entirely in the smarts.bio condition, and were identified by inspection during the study rather than by a rule fixed in advance. The six protein-design cells in the smarts.bio condition carry a run date of 12 November, after a fix to the tool server that had served that category and five days after the other conditions completed; one of them is among the six cells described here, and an audit note dated 6 November describes two of the others as having already run, which the run record does not reflect. Comparator runs that ended on timeout were left as they were. Start times for every run are in the released record, and the effect of this handling is quantified in §5.9.

2.4 Grading and audit

Twenty-one of the 46 tasks in the primary specification declare a machine-checkable answer type (two exact-match, one numeric-tolerance, eighteen set-membership), and twenty-two of the 48 as authored. Declaring one is not the same as receiving one: of the 84 primary runs on those tasks, 70 returned an answer the check could read, while seven timed out and seven answered in a form the check could not parse. The deterministic layer therefore carries 70 of the 184 primary runs. The other 114 rest on the automated judge alone, to which the reliability findings reported below apply directly: 100 of them are the four runs each on the 25 tasks that declare no checkable type, and 14 are runs on declaring tasks that returned nothing the check could read. The frozen ground_truth is prose, which cannot be string-matched, so the eighteen set-membership checks were operationalised into machine-readable form after the runs had completed, in a separate file that leaves the frozen task set unedited. Each check was derived from its own task's frozen ground truth or rubric text rather than from any answer it would grade; that ordering is a property of how they were written and not something the released files can prove, so a reader who doubts it should weigh the deterministic layer accordingly.

All answers were additionally graded by a blinded rubric judge on a 0–3 scale: 3, correct and sourced; 2, correct with gaps; 1, partially correct; 0, wrong, unjustified refusal, or no usable answer. The judge received each answer with platform and tool names stripped, together with the rubric and ground truth, and never saw which condition produced it.

One task, scored. Task expr-001 asks, in the user's words, "Which genes are differentially expressed in this count table, and in which direction?" The fixture holds eight genes, of which GENE1, GENE4 and GENE7 are raised fourfold in the treated samples and GENE2, GENE5 and GENE8 lowered fourfold. A smarts.bio run scored 3: it read the file, named all six genes with the correct direction, and observed that median-of-ratios size factors are all near 1.0, so the larger treated library totals are caused by the upregulated genes rather than by sequencing depth. The untooled control scored 0: with no tools attached it emitted a shell command and a directory listing, complete with invented file sizes, permissions and timestamps, and stopped there, naming no genes at all. The judge flagged the smarts.bio run's cited process identifier as fabricated; the audit found that identifier verbatim in the tool output returned earlier in the same transcript and withdrew the flag (§3.8). Both transcripts are released. The judge was claude-opus-5 at default sampling, the same model that generated the answers. Because that model produced every condition's output, self-preference is symmetric across conditions and cannot order them, but it may compress or expand the scale uniformly, and an independent judge family is required before these scores are treated as absolute.

Because an automated judge is itself an instrument with unknown error characteristics [9], every graded answer was re-checked against primary sources in a separate audit layer, reported alongside the judge's raw output rather than silently replacing it. Of ten hallucination flags the judge raised, eight were refuted against primary sources. In one instance the judge called a PubMed identifier fabricated when it was the cited structure's own primary citation. We therefore do not report a hallucination rate derived from the judge. Judge scores are never edited in place; corrections exist only in the audit layer, so both readings remain inspectable.

Two limits of the audit must be stated. It was performed by the authoring party and was not blinded to condition. And the study design called for an independent human to re-check a random 20% of answers plus every judge–audit disagreement, with an agreement rate reported; that human verification was not carried out, so no inter-rater statistic is available and the audit layer is itself unaudited.

2.5 Analysis specifications

Two specifications are reported throughout, because each is defensible and the choice between them affects the magnitudes. Neither was specified before data collection; both were constructed during analysis. No pre-analysis plan was registered, and both specifications are therefore reported in full rather than one being selected.

Primary (audit-corrected). The two defective tasks of §2.2 are excluded from all conditions, giving n = 46 in every condition; audit corrections are applied where the audit disagreed with the judge; timeouts score 0. No condition carries an arm-specific exclusion. An earlier version of this analysis excluded one smarts.bio cell in which a compute quota was exhausted mid-run; that run nonetheless returned an answer and was graded 2, so it is retained. Excluding it would have removed the single task on which smarts.bio was outscored by both comparator conditions, while comparator runs that returned nothing were scored 0, applying to one condition an exclusion standard not applied to the others.

Sensitivity (raw). All 48 task records are retained in every condition, no audit corrections are applied, and timeouts score 0. This specification requires no audit material and is reproducible from the run-level file alone.

An audit correction is applied only to a run that started on or before that audit's date, so a cell re-measured after being audited carries its own score rather than a stale correction. This rule was devised during analysis, not specified in advance, and is therefore a post-hoc choice. The rule discards six audit rows in total, and all six fall in the authoring condition. Five of the six record agreement with the judge and so change no score. The sixth, a CRISPR guide-design task, is its only material effect, and it runs against the authoring condition: it discards a correction that would have raised that condition's score from 1 to 3. Three repetition-2 records exist for three control-condition tasks only; because they do not form a balanced repeated-measures design, they are excluded from both specifications.

2.6 Statistical approach

The analysis is descriptive. Each task–condition cell has one primary run, so the data cannot estimate run-to-run stochastic variability. We report means, score distributions, completion rates and paired task-level win/tie/loss counts. Exact sign tests are the only inferential statistics reported. All six pairwise tests are given in §3.7, not only those involving the authoring condition, and because six are computed on the same data we report Holm-corrected values alongside the raw ones. Every comparison that reaches conventional significance uncorrected also survives the correction, including smarts.bio against Biomni, whose adjusted value is 0.025. §3.7 states what these tests can and cannot support where the numbers appear: they test whether two conditions differed on these particular tasks, not whether one platform is reliably better than another. No confidence intervals are reported, and this is a design limit rather than an omission. An interval around these means would treat the task set as a random sample drawn from some wider population of bioinformatics tasks. It is not one: it is self-authored, and its distribution across categories is a choice (§5.1). An interval computed on that basis would express a precision the design cannot support. Standard deviations, where given, describe dispersion across the fixed task set and are not standard errors.

2.7 Relation to published benchmarks

This is an execution-oriented, fixed-model comparison of tool-server endpoints, not a leaderboard of models and not a comparison of the platforms as deployed (§2.1). It is therefore not directly comparable to LAB-Bench [1], BixBench [2], PromptBio-Bench [6], BiomniBench [7] or BioAgent Bench [8], all of which vary the model or the harness and use different task sets and scoring protocols. Their reported scores and ours should not be placed on a common axis. In particular, the score here summarises the judged outcome of a run and is not a measure of workflow validity, process quality or robustness, each of which those frameworks address directly and this one does not. Where §4 draws on a published result from that literature, it compares the direction of an effect and never its magnitude, which is the only comparison these differing protocols support.

3. Results

The study's central observation is stated first, because the remaining results are decompositions of it. Across all 46 tasks the untooled control averaged 1.00 and the three tool-enabled conditions pooled averaged 2.33, but that single difference is an average of two unlike regimes (Figure 2). Where a task asks for a fact the model has read, the gap is negligible. Where a task asks for a computation over the user's own data, the gap is most of the scale.

3.1 Overall task performance

Every tool-enabled condition outperformed the control on both mean score and acceptable-task proportion, under both specifications. The ordering of the four conditions is identical in the two analyses; only the magnitudes shift (Figure 3, Table 1).

Because the six protein-design tasks of §3.4 are the category most likely to favour the authoring condition's managed GPU catalogue, the primary means were recomputed with that category removed. Over the remaining 40 tasks they are 2.73 (smarts.bio), 2.38 (Biomni), 2.10 (Galaxy) and 0.97 (control), with acceptable rates of 92.5%, 82.5%, 72.5% and 30.0%. The ordering is unchanged, and the smarts.bio mean rises by 0.03 rather than falling, because it scores 2.50 on the design tasks against 2.73 elsewhere. The category therefore does not generate the reported margin.

The control condition answered 28.3% of tasks acceptably and scored zero on 19 of 46. Its failures are not marginal degradations. Transcript inspection shows the characteristic failure mode of an untooled model asked to compute: it produces a plausible value rather than a retrieved one. In one run it emitted a simulated shell command followed by a fabricated directory listing (complete with file sizes, permissions and timestamps) and then reasoned from that invented observation as if it were a measurement.

3.2 Distribution of scores

Means can conceal whether a condition fails softly or catastrophically. The distributions differ in shape, not only in central tendency (Figure 4): the control's mass sits at 0 and 1, while every tool-enabled condition's mass sits at 3.

3.3 Performance by task category

Read as a practitioner would: almost nothing in the NGS or expression categories worked without tools, at 0.00 and 0.33, while database lookups and variant interpretation were largely answerable from memory. The categorical breakdown (Figure 5) is the study's central evidence, because it shows where tool access matters and where it does not. The division is not by difficulty but by where the answer lives: database lookups and variant interpretation ask for facts the model has already read, while NGS pipelines and expression analysis ask for a computation over data the model has never seen.

Category means carry substantial uncertainty. Five of the eleven categories contain only two or three tasks, where a single task moves a mean by 1.0 to 1.5, so no gap should be read to two-decimal precision. Only database lookups, sequence analysis, NGS pipelines and protein design contain enough tasks to support even informal comparison between conditions. A gap of 0.12 on an eight-task category and a gap of 0.17 on a four-task category are both well inside the noise this design can resolve, and neither is evidence that tools help a little. The pooled tool-enabled mean in Figure 2 averages three conditions that differ substantially from one another (Figure 3): it isolates the tooled/untooled contrast, and no ranking among the three can be recovered from it.

3.4 Computational protein design

Protein design and structure prediction was the hardest category for every condition: no condition averaged above 2.50, against 3.00 ceilings elsewhere (Figure 6). Tasks separable by database lookup (ligand binding affinity, two-chain complex prediction) were answered well by several conditions; tasks requiring a generative model to be run (de novo binder design, enzyme thermostabilisation, mutation stability ranking) separated them.

One result contradicted our stated expectation. We had predicted that managed GPU compute would be the clearest point of platform differentiation, on the assumption that a general workflow platform would not offer it. Galaxy scored 3 on ligand binding affinity, matching the best condition: Galaxy provides docking, and its 2024 platform update explicitly describes integrating general-purpose GPU access [5]. The differentiation we expected holds for generative design but not for established ligand docking, and the prior was too strong.

3.5 Completion and reliability

Completion is a distinct dimension from answer quality, and the two do not move together. Fifteen runs across the tool-enabled conditions produced no answer at all within their fixed budget: one for smarts.bio, six for Biomni and eight for Galaxy (Figure 7). The control condition never timed out, because it never waits on external execution, an absence of timeouts that is not comparable to the reliability of a condition that does.

3.6 Driver cost

Recorded model-driver cost, meaning the model tokens consumed to operate a condition across the whole suite, was $175.65 (smarts.bio), $52.61 (Biomni), $124.61 (Galaxy) and $12.76 (control). Much of the spread arises from the polling loop, in which every session resume is a fresh model turn carrying the accumulated conversation, so a condition that runs long jobs pays repeatedly to wait for them.

Per acceptable answer the same totals give $4.08, $1.46, $4.02 and $0.98 in that order, on which smarts.bio is the most expensive of the four conditions and Biomni by a wide margin the cheapest of the three tool-enabled ones. These are driver costs only, and they are not a cost-efficiency ranking. Each platform's own CPU and GPU time is not comparably observable across vendors and is excluded entirely. Driver cost also went unrecorded for fourteen of the fifteen timed-out runs, undercounting smarts.bio by one run, Biomni by six and Galaxy by seven of its eight. The one exception, a Galaxy run resumed twenty times before it timed out, recorded $7.10 and is included in the total above. These figures therefore measure what it cost to operate each condition through this harness, not what the underlying work costs. The control's $0.98 illustrates the distinction, since it buys an acceptable answer barely a quarter of the time. §5.7 takes up the consequences.

3.7 Paired comparisons

Because every condition saw the same task identifiers, paired comparison is possible (Table 2). The tool-enabled conditions agree with one another far more often than they differ: smarts.bio and Biomni produced identical scores on 29 of 46 shared tasks. On the tasks where they differ smarts.bio scores higher 14 times against 3 (exact sign test, p = 0.013; Holm-adjusted across the six comparisons, 0.025), and against Galaxy 21 times against 4 (p = 0.0009; adjusted 0.0036). All six pairwise tests are reported in Table 2 rather than only those involving the authoring condition. Five reach conventional significance and survive the correction; Biomni against Galaxy does not, at p = 0.134. The comparison against Biomni is also sensitive to the cells of §5.9: substituting the earlier recorded scores for those cells moves it to 14 against 6 (p = 0.12), so it should be read as suggestive rather than established. The comparison against Galaxy survives the same substitution. With one run per cell these tests establish that the conditions differed on these particular tasks, not that one platform is reliably better than another; they are reported because the counts in Table 2 invite the calculation.

3.8 Provenance and identifier fabrication

Every PubMed identifier, DOI, UniProt, PDB, ChEMBL and PubChem accession emitted by any condition was resolved against its issuing registry: 126 identifiers, 124 registered, 2 absent (Table 3). Both absent identifiers were DOIs sharing a single non-existent stem, appearing independently in the control condition and in one tool-enabled condition. That an identical fabricated stem recurs across unrelated conditions implicates the shared base model's priors rather than any platform, a finding in its own right: tool access does not eliminate fabrication, it displaces it. Where an answer was assembled from retrieved records the identifiers resolved; where the model filled a gap from memory, they did not.

The control condition cites a source in 18 of 46 answers. Its low absolute count of fabricated identifiers reflects how rarely it attempts a sourced claim, not unusual care.

One asymmetry in Table 3 requires explanation. Galaxy cites a source in 35 of 46 answers but emits only eight registry identifiers, against 57 and 50 for the other tool-enabled conditions. This is a difference in the kind of provenance offered rather than its quantity: of those 35 answers, 18 cite Galaxy-internal object identifiers and 10 reference history items or dataset numbers, all of which are checkable by the user who ran the job but resolve against no public registry. The registry audit can therefore say nothing about the correctness of Galaxy's provenance, and its single absent DOI should not be read against a denominator of eight as though that were comparable to 57.

4. Discussion

The tooled–untooled contrast is the robust result of this study. What makes it interpretable rather than merely large is that the control fails precisely where an answer cannot be recalled, because it depends on data the model has never seen. Prompting alone is unlikely to close that gap, since the missing ingredient is execution rather than reasoning; we varied only tool access and never the prompt, so that reading is an interpretation of the mechanism rather than something this design measured.

The same effect has been measured independently, though not by a disinterested party: Biomni's own evaluation reports an average relative gain of 402.3% over an untooled base language model across eight realistic biomedical benchmarks [3,4], using a different base model, different tasks and a different scoring protocol. That two unrelated designs recover the effect in the same direction is stronger evidence for the tooled–untooled contrast than either study alone. The magnitudes are not comparable, and ours is not calibrated to support a claim about size: this design establishes direction only. It is also consistent with the gap BixBench reports between knowledge recall and open-answer analytical performance [2], and with BiomniBench's observation that the agent harness shifts scores by more than the difference between successive model generations [7].

The between-condition contrast is weaker than it looks. The three tool-enabled conditions span 0.70 points on a single run per cell with no error bars, and smarts.bio ties with Biomni on 29 of 46 paired tasks. The two sign tests of §3.7 reach conventional significance but establish only that the conditions differed on these tasks; the ordering does not establish a ranking of platform capability.

Reliability behaves differently from accuracy and may matter more in practice. Fifteen runs produced nothing. For a working scientist, a condition that is marginally less accurate but finishes may be preferable to one that is slightly better when it works and silently fails up to one task in six. We recommend that future comparisons report quality conditional on completion alongside an intention-to-complete score, as done here, since the two can order conditions differently.

An automated judge needs an independent auditor. Eight of ten hallucination flags were false positives. One propagated into our own draft analysis before being caught: the judge declared PMID 9631087 a fabricated citation for PDB entry 1GFL and offered PMID 8848045 as the correct one. The first is the structure's own primary citation; the second is an unrelated vision-science paper. The substitution survived in an internal analysis document until the registry audit reached it. The LLM-as-judge literature reports high aggregate agreement with human preference [9] but also systematic position and verbosity biases. Aggregate agreement can evidently coexist with a specific sub-judgement, here fabrication detection, that is unreliable enough to be unusable. Benchmarks relying on an automated judge without a verification layer should be assumed to carry errors of comparable magnitude, and the direction of those errors need not be symmetric across conditions.

What this design cannot distinguish. The benchmark cannot separate a platform that lacks a capability from one that possesses it but failed to surface it to the model. Several low scores trace to the model never discovering a tool that existed, which is a property of the tool-description interface rather than of the underlying compute. An unreachable capability is no capability to a user, but to a developer the distinction separates building something from documenting it. Nor does this design measure workflow reproducibility, provenance completeness, governance, multi-user operation, or usability for humans rather than agents. These are central to a platform like Galaxy [5], and none is captured by a task-outcome score. Process-level frameworks [7,8] and structured-output comparison [6] address exactly these dimensions and are complementary to, not competitors of, the present measurement.

5. Limitations

We regard the tooled-versus-untooled contrast as sound and the between-condition ordering as provisional. The reasons follow, in descending order of how much they threaten the latter.

5.1 Benchmark authorship

This benchmark was designed, run, graded and audited by a party to the comparison. That is a structural conflict, and no internal procedure removes it; the safeguards adopted here should be read as constraints upon it rather than as a remedy for it. Five safeguards were adopted. The task set, rubrics and ground truth were frozen before the first run (§2.2). Every condition received the identical model, system prompt and task text, and differed only in tool access (§2.1). The rubric judge was blinded to condition (§2.4). Judge scores are preserved unedited, with audit corrections held in a separate layer so that both readings remain inspectable (§2.5, §7). Both the audit-corrected and the raw-score specifications are reported in full rather than reconciled after the fact, and every figure in §3 can be recomputed from the released files. What none of that addresses is that the task set is self-authored, and that the distribution of categories across it is itself a choice which may favour the authoring platform. On the category where that objection is sharpest, the six GPU protein-design tasks that most favour a managed GPU catalogue, it can be tested directly: removing them leaves the ordering intact and raises the smarts.bio mean by 0.03 (§3.1). That addresses one category out of eleven, and not the more general point that the weighting of the whole set was chosen by an interested party.

Audit attention was also asymmetric: 57 of 126 identifier checks and twelve of the primary-source audits concern our own condition, against two to seven for each other condition. Examining our own answers more closely than anyone else's is methodologically wrong irrespective of what it finds. Its measured effect did not run against the authoring condition, and we state that plainly because the opposite would have been the more comfortable finding. Every audit correction in the released layer is an upgrade: the authoring condition gains a net five points across two upgrades with no downgrades, Biomni gains five across three, and Galaxy three across one. Examining our own answers more closely therefore did not surface more of our own errors; it produced corrections of the same sign and similar size as those applied to a comparator we examined less. The asymmetry of attention remains a defect of the design, but it cannot be defended on the ground that it cost us anything, and a reader should weigh it as an unbounded risk rather than as a tested and harmless one. A differently distributed audit might have found more in the comparators, so the asymmetry remains a defect of the design rather than a neutral feature of it. Independent task design and blinded replication remain necessary before the ordering can be considered established.

The shared system prompt deserves specific mention, because §2.1 presents it as a fairness guarantee and it is also a confound. We wrote that prompt, and we wrote the tool descriptions for one of the four conditions. Since tool discovery is explicitly part of what the study measures (§2.2), a prompt whose conventions match our own tool descriptions advantages our condition by construction, and we have no measurement of how large that advantage is. Giving each platform a prompt tuned to its own conventions would introduce a different bias. Neither choice is neutral, and the magnitude of the one made here is unmeasured.

5.2 The comparator conditions may not represent the comparator systems

A platform reached through a tool-server protocol exposes its tool inventory, not necessarily the agent architecture its designers built around those tools. This is a first-order concern for Biomni, whose published system executes code as its action interface and reports a 20.4% advantage over an ablated variant using conventional function-calling [3,4]. We could not verify from outside which of these our access path engaged. If it engaged the latter, this study compared our full platform against a competitor's tools minus its planner, and any reader who took the conditions in §3 for the platforms themselves would be badly misled.

The concern extends, less quantifiably, to Galaxy: a workflow system whose stated value lies in reproducible, provenance-tracked, shareable analyses [5] is poorly represented by single-shot tool invocation. Both effects run against the comparators and in our favour, and neither is bounded by anything in our data. One factor runs the other way and is recorded here for symmetry: as §2.1 sets out, 35 of Biomni's tools are natural-language wrappers around its own model, so part of that condition's work is done by model computation the fixed-model design does not control, and it is most concentrated in the one category Biomni wins. The smarts.bio condition draws on two such endpoints of its own, less often; the direction of the net effect is not determinable from these data. This is why §2.1 scopes each condition as a tool-server endpoint rather than as a platform, and why the Results speak of conditions throughout. A comparison of the platforms themselves would require exercising each through the interface its designers intend; this study does not do that, and its numbers should not be read as though it had.

5.3 Unequal measurement across the study period

Runs span 2–12 November 2026. The comparator platforms are third-party hosted services, measured as encountered, once. The authoring platform was under active development during the window and was measured on more than one occasion. The margin between the authoring condition and the others should therefore be read as an upper bound rather than a point estimate. We state this explicitly because per-run timestamps are included in the released data, from which it is in any case recoverable.

5.4 Single run per cell

The pre-specified design called for three repetitions; one was run. Agentic systems are stochastic, and a single observation cannot estimate repeatability. The three available repetition-2 records cover only three control-condition tasks and do not remedy this. This is the single largest obstacle to treating any between-condition difference as established.

5.5 Task-material defects and inconsistent exclusion standards

Two tasks were excluded post hoc for defects in their own material (§2.2), and the identities of both are released with the data. A third task, germline variant calling, carries a known ground-truth defect: its reference answer names variants absent from the supplied alignment, having been frozen against the wrong fixture. It was corrected within the audit layer rather than voided, which is an inconsistent application of the standard applied to the other two. It is also not a neutral case: on that task smarts.bio scores 2 and Galaxy scores 3, so the choice to repair rather than void preserves a comparator's win and our loss, but it was still made ad hoc. A single rule applied to all three defective tasks would be preferable, and we report what it would cost: voiding the germline-calling task as well gives means of 2.71, 2.36, 1.98 and 1.02 over 45 tasks, a shift of at most 0.06 in any condition, with the ordering unchanged. The primary analysis is reported alongside the raw specification for the same reason: the two specifications differ by at most 0.15 in any condition and reorder nothing, so none of this handling carries the result.

5.6 Execution environment and timeout attribution

The Biomni tool container, the only condition served from a local container rather than a remote endpoint, was inadvertently left running at full utilisation of one CPU core on the benchmark host for three days under binary translation. Runs executing alongside it have inflated wall times, and we cannot exclude that it contributed to that condition's timeouts. Because timeouts score 0, this is a potential source of error in the authoring platform's favour affecting up to six of the fifteen non-completions in Figure 7. Host telemetry sufficient to quantify it was not retained.

5.7 Tier asymmetry and incomplete cost accounting

Comparator conditions ran on free tiers; the authoring condition ran on its own paid infrastructure. Rate limits and queue priority were not controlled, so some portion of the reliability difference may reflect tier rather than platform. Separately, platform compute cost is absent and model cost is missing for timed-out runs (§3.6), so the figures cannot support a total-cost-of-ownership comparison.

5.8 Absence of an external calibration anchor or human baseline

All 48 tasks are our own. The pre-specified design called for several items drawn from published benchmarks such as LAB-Bench [1] or BixBench [2] as a difficulty anchor; none were included. A reader consequently has no model-independent measure of how hard these tasks are, and cannot position our scores against published results.

There is no human baseline either. Related work routinely supplies one: Biomni reports 74.4% against an expert 74.7% on database question answering and 81.9% against 78.8% on sequence questions, and benchmarks its cloning protocols against both a trainee and a senior expert [3,4]. We cannot say whether a mean of 2.70 is close to what a competent bioinformatician would score on these 46 tasks, or far below it. Without that anchor, every score reported here is meaningful only relative to the other conditions in this study, and carries no absolute interpretation.

5.9 Cells that were run again

Re-running a run that failed for reasons belonging to the harness is ordinarily sound practice, and one cell was re-run on that basis. Most, however, were re-run after platform-side failures, which §2.3 scores on what the user received; re-running them departs from that rule.

At least six cells were run again, and the audit layer recorded a judge score for each of those six beforehand. The 5 November batch contains eight runs at five-to-seven-minute intervals, and an audit note dated 6 November describes two protein-design cells as having run in a batch that the run record dates to 12 November, so the true number may be higher and the earlier scores do not survive for the additional cells. The substitution below therefore covers the six whose earlier scores are recorded, not necessarily every cell that was run twice. Each earlier score is taken on the same basis as the published cell it replaces, which is the audited score where the audit returned a verdict and the judge score otherwise; one of the six, a CRISPR guide-design task, scored higher before being run again than after. Substituting them lowers the authoring condition's mean from 2.70 to 2.52 and leaves the ordering of the four conditions unchanged. The execution gap of §3.2 falls from 1.33 to 1.28. The paired comparison against Galaxy remains significant at 20 to 7 (p = 0.019); the comparison against Biomni does not survive the substitution, moving from 14 to 3 (p = 0.013) to 14 to 6 (p = 0.12).

The superseded runs were not retained, because the run identifier is the file name and running a cell again overwrote it. The figure above is therefore a partial reconstruction from the audit layer rather than a measurement of the original record, and because it covers only the cells whose earlier scores survive, the true effect may be larger. The six scores it rests on are released in results/superseded_scores.csv, and analyze.py recomputes the substitution.

5.10 Scope

One model, one task set, one measurement window. The study does not establish whether the pattern holds for other models, other scientific domains, other data types or other platform configurations, nor does it evaluate security, governance or behaviour at production scale.

6. Conclusion

With the agent that plans and calls tools held fixed, whether an analysis can be executed is the first-order determinant of performance on realistic bioinformatics tasks. An untooled frontier model failed roughly three quarters of these tasks and failed almost completely on those requiring computation over user-supplied data, while every tool-enabled condition at least doubled its acceptable-task rate. This contrast held under both analysis specifications and does not depend on any comparison between the platforms.

The relative ordering of the three tool-enabled conditions is the same under both analysis specifications, but it is provisional in strength. Seven factors bear on it: single-run measurement, self-authored tasks and prompts, asymmetric audit attention, unequal measurement across the study period, tier differences, unquantified host contention, and the likelihood that the comparator conditions exercised tool inventories rather than the agent architectures built around them. The last is the most serious. Each is reported rather than resolved. A publishable comparison of platforms would require independent task authorship, repetition of every cell, symmetric audit coverage, a controlled execution environment, a human performance baseline, and access to each system through the interface its designers intend. The finding that does not depend on those requirements is narrower and more robust: within the conditions evaluated here, with the model held fixed, whether a tool layer was attached was a stronger determinant of task score than which of the three endpoints it was. The control completed every task it was given; what it could not do was produce a correct answer.

7. Data availability

The frozen task set with rubrics and ground truth, the run-level record for every run, both audit layers, and the raw transcript of every run in that record, including the runs that failed or timed out, are released at github.com/smartsbio/bio-agent-platform-benchmark, under the MIT licence for code and CC BY 4.0 for the task set, the run record and the transcripts. Judge scores are preserved unedited; audit corrections reside in a separate layer so that the original and corrected readings are both inspectable. At least six cells in the smarts.bio condition were run again during the study (§2.3); the superseded runs were not retained, and the scores recorded for them before they were run again are released in results/superseded_scores.csv. The task set is released as it was run. A second file carries the same set with the two defective tasks of §2.2 repaired, together with a changelog recording each repair; it was prepared after the run and never executed, so no figure reported here derives from it, and it is published for the use of anyone repeating the study. Both analysis specifications of §2.5 are implemented in a single released script, analyze.py, which takes no arguments and requires nothing beyond a standard Python 3 installation; running it reproduces every condition-level and category-level figure reported in §3 from the three primary files. The repository is the citable record of this study. Its first public commit identifies the released artefacts exactly, and should be cited alongside this report; it does not, as §2.2 states, evidence the date on which the task set was frozen, because the set was not under version control at that time. The same artefacts are deposited as a versioned archive at Zenodo under doi:10.5281/zenodo.24559143, which is the identifier to cite for the exact version reported here. Later versions, should the corrections of §8 require them, are deposited as new versions of that record rather than replacing it.
